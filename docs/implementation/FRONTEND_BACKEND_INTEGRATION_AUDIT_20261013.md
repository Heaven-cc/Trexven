## Genuinely missing/deferred backend functionality

Expenses already exist with `business_id`, `amount`, category, description, payment method and `created_at`, protected by finance and branch policies. The existing `get_trexven_financial_summary(p_business_id,p_start,p_end)` returns gross sales, sale collections, repayment collections, refunds, current receivables/overdue balances and net collections. Receivables/overdue are current balances, not historical balance snapshots. There is no need to duplicate this reporting service.

For expenses, the minimum compatible addition, if needed by future approved wiring, is an authorized interval expense aggregate or additive summary fields using the existing table. Define the actual posting-date/timezone and any reversal semantics before implementation. No replacement expense table or guessed amounts are justified. The inspected Finance screen has no expense-entry controls.

For profit, cost capture/access is explicitly deferred by the existing purchase-cost migration: authenticated clients cannot SELECT `products.cost_price`, and `view_profit` is denied. There are no `sale_items` cost fields. A future approved implementation needs a defined cost basis, immutable cost-at-sale evidence, handling of unknown historical costs and returned stock, an owner-authorized aggregate with interval/timezone semantics, and explicit grants/RLS review. Preserve unknown historical results rather than treating them as zero; do not backfill invented costs. These additions and permission changes are a proposal, not applied migrations. The present UI would still need approved wiring.

Actual retail provider settlement verification, live Google/email callbacks, real Groq success, hardware scanning and push delivery were not exercised. Existing transaction RPCs enforce the authorized caller's explicit payment confirmation and noncash evidence; this audit does not prove independent payment settlement. These are verification limits, not evidence that a configured provider is broken.
